## 修复过的问题

- 存储检查错误地拒绝 macOS `/var` 与 `/tmp` 系统路径别名。现先规范化父目录，再严格检查受管目录本身。
- `os.FileInfo.Sys()` 的所有者类型断言不可靠。现使用 `unix.Lstat`，对根与子目录强制校验 UID、私有权限和目录类型，并有错误 UID 回归。
- 退出只发送信号而未等待 Go 清理。现通过 stdin EOF 和进程退出等待完成正常关闭，不靠固定 sleep。
- 强制终止后的清理警告可能丢失。现记录强制终止并保留警告，避免自动重启后显示正常状态。
- 新拖入配置可能复用上一轮补选凭据。现新导入清空补选，只有当前导入的重验保留补选。

## 2026-11-04：退出死锁修复

旧版从 Swift Task 调用 `NSApp.terminate` 后，AppKit 的退出等待循环阻塞 MainActor 上的异步清理任务。实际进程采样与隔离复现均确认此路径。现在将退出请求安排到主 RunLoop，先结束原 Swift Task，再由系统等待清理；保留 `terminateLater` 与系统退出回复机制。

新增 `scripts/test-termination.sh`，直接编译生产退出代理及 `quit` 实现，以可控异步清理覆盖正常退出、失败后重试、重复点击、模型未初始化四种情况。同一测试在旧实现上因死锁失败，修复版全部通过。完整 Go race、13 个 Swift 测试通过。真实 App 使用临时空存储启动后，标准系统退出请求成功，App 正常退出，后台释放存储锁；该测试没有建立网络连接。

## 2026-11-05 helper 控制 socket 不跟随符号链接（Issue #34）

来自 #32 的同一次特权边界审查。helper 原先用完整路径调用 `os.Chown`、`os.Chmod` 设置控制 socket，这两个调用会跟随符号链接；而运行目录的父目录 `/private/var/run` 对 `daemon` 组可写。现在 socket 在 `umask 0177` 下创建，一开始就是 `0600`；属主和权限改用带 `AT_SYMLINK_NOFOLLOW` 的 `Fchownat`／`Fchmodat` 设置，之后再用 `Lstat` 确认它是 socket、属主是受控用户、权限是 `0600`，否则 helper 退出。

新增 `TestSecureSocketDoesNotFollowLinks`。用原来的做法时，该测试检测到链接目标被修改而失败；修正后，链接被拒绝、目标不变，真实 socket 被收紧为 `0600`。`go test -race ./...`、`go vet` 和 `bash scripts/test.sh` 通过。root 下的启动路径需要安装新的 helper 才能实机执行，本次未重新安装。

## 2026-11-05 节点测试绑定 Nebula 隧道接口（Issue #36）

## 2026-11-05 导入校验加固（Issue #38）

Codex 对普通用户后台的导入与存储做了只读审查，报告了 5 项问题，我逐条对照代码核实。本 Issue 修复其中 3 项：

- **错误字段回显未知键名。** 未知字段的键名原先直接成为 `Problem.Field`；如果复制粘贴把 PEM 放进了键名，凭据会出现在错误响应中。现在只回显符合字段名格式的键名，否则只返回 `config` 或 `pki`。
- **YAML 对象规模。** 实测 `yaml.v3` 解码 map 的开销是平方级：单个对象 1 万、2 万、4 万个键分别耗时 156 ms、492 ms、2.2 s，2 MiB 内约 20 万个键会耗时约一分钟。这会阻塞后台，也会占住 root helper 的 `validateInline`。现在解码前限制每个对象最多 4096 个键，约 2 MiB 的 20 万键文件在 0.18 s 内被拒绝。
- **受管副本大小。** 内嵌凭据并重新缩进后，配置可能超过 `Load` 的 2 MiB 读取上限。现在保存前检查，超出时返回 `config_too_large`。

新增 3 个测试，修正前全部失败、修正后通过。

另外两项的处理：存储写入缺少文件和目录的同步，另立 Issue。自定义 `--store` 位于不可信父目录时存在目录替换竞争；GUI 始终使用 `~/Library/Application Support/NebulaGUI`，`--data-dir` 只用于开发和测试，因此只记录，不修改。

## 2026-11-05 受管存储断电一致性（Issue #40）

同一次后台审查发现：受管存储在进程被终止时安全（rename 是原子的），但断电后不一定一致。`config.yaml` 写入后没有同步，rename 之后也没有同步目录；更新后立即清理旧版本、删除时改名后立即删除文件，都可能在断电后留下指向已删除版本的索引。

新增 `TestManagedConfigWriteNeverFollowsOrReplaces`：受管配置不会写穿符号链接，也不会覆盖已有文件。断电本身无法在单元测试中模拟，这部分依据代码审查确认顺序；现有的存储、更新、回滚和删除测试全部通过。`go test -race ./...`、`go vet` 和 `bash scripts/test.sh` 通过。

  2. 每 3 秒轮询一次，即使内容没变也会给 status／authorization／events／recoveryText 赋值，导致整窗重绘。另外内核按 Go map 列出节点，顺序每次不同。已改为只在内容变化时更新，后台按固定顺序返回节点。修复后空闲状态下每 3 秒一次、10–18% 的 CPU 尖峰消失。
  3. 用户点击时，约 38% 的主线程忙碌时间花在 NSButton 经 CoreUI 测量尺寸上。经用户同意，工作区按钮改用 SwiftUI 自绘的 `NebulaButtonStyle`，弹窗仍保留原生按钮。
  4. 余下的开销集中在 SwiftUI 内部重建页面并重新布局，自有代码每项都不到 15 ms。已改为访问过的页面常驻，切换时只改变可见性。
- 测量方法：System Events 发送的 ⌘ 快捷键没有真正切换页面，这部分数据作废。辅助功能点击会触发无障碍树重建，绝对值偏高，只用于前后对比。同一方法下，概览／节点／配置／日志的切换耗时由 126／186／204／355 ms 降至 70／61／65／67 ms。停留在日志页时，主线程开销由约 82 ms/s 降至约 16 ms/s。用户点击期间，辅助功能处理只占 0.4–0.6%，排除了常驻辅助工具导致卡顿的可能。
- 用户反馈：页签只有点中中心才响应。原因是 `PressStyle` 没有声明可点击区域，SwiftUI 只把绘制出的像素当作命中区域，未选中页签和侧栏行的背景透明。已改为整个外框可点击。

## 2026-11-08 macOS 13 上 helper 升级失败（Issue #60）

验收 #57 时，在 macOS 13.7.8／Intel 上通过 GUI 把 helper 从 0.3.1 升级到 0.4.0，结果失败，界面只显示通用提示。旧 helper 的 pid 没变，没有残留锁或临时文件。用户手动运行同一份升级脚本（加 `set -x`，并返回错误码），得到退出码 64：脚本已执行到 `launchctl bootout --wait`，随后回滚。用不存在的服务名验证：`launchctl bootout --wait …` 打印用法后以 64 退出，不带 `--wait` 则正常返回 3。该参数从 98da84c 起使用；升级、失败回滚（`|| true` 掩盖了失败）和移除三处都受影响。AUTHORIZATION.md 原先已注明“最低系统版本的实机兼容仍待验证”。

修复：脚本内新增 `stop_helper`，执行不带等待参数的 bootout，再有界轮询直到 launchd 不再列出服务、原进程已退出，三处统一调用。`UpgradeTests` 中的 launchctl 替身原本要求必须带 `--wait`，现改为模拟 macOS 13（带 `--wait` 返回 64），并增加 bootout 后服务短暂残留的场景和移除测试。

本机在隔离 Swift 工程中运行实际 NebulaClient 源码：`UpgradeTests` 与 `AuthorizationTests` 共 11 项通过。用同一替身运行修复前的脚本，升级失败退出码为 64，移除为 75，与实机现象一致。实机升级随 #57 验收一起完成。

实机（macOS 13.7.8／Intel，2026-11-08）：用叠加了本修复的 #59 CI 安装包，通过 GUI 先后完成两次升级：0.3.1 → 0.4.0、0.4.0 → 0.4.1。两次都换了新 pid，只有一个 helper 进程。已安装的 helper 与包内 SHA-256 一致；helper 和启动项为 root:wheel、0755／0644，socket 属于登录用户、0600；`-health` 通过；没有残留的备份文件或安装锁。之后通过 GUI 连接真实网络，隧道正常建立。

## 2026-11-08 节点延迟持续监测（Issue #44）

节点页可见、隧道已启动时，GUI 每 5 秒请求普通后台的 `sample`，对活动隧道节点的每个地址各发 1 个 ICMP。普通后台校验以下条件：已连接、地址数不超过 64、地址在当前网段内、两次请求间隔至少 2 秒。并发不超过 8，每个地址最多等 1 秒，整轮最多 4 秒。GUI 只在内存中为每个地址保留本次连接最近 60 个样本，连接变化时清空。设计见 [日常体验](DAILY_USE.md#节点延迟监测44)。

本机：`go vet`、`go test -race` 通过（新增 sample 拒绝、按地址顺序返回、并发上限、整轮超时 4 项）。隔离 Swift 工程中客户端测试 46 项通过（新增 LatencyTests 6 项）。CI（M4）跑通全部 Swift 测试（含采样只在节点页可见时进行、旧连接结果丢弃、断开后清空），并生成浅色和深色的 `monitor` 预览截图，其中包括展开后的详细曲线。

实机（macOS 13.7.8／Intel，真实网络、5 个活动地址）：汇总卡片显示中位延迟、分级和分段条；各节点行的折线随采样更新，较慢节点显示为红色，未回复的点断开折线。实机中发现一次未回复会把整条折线染成灰色，已改为按最近一次有回复的样本着色。用户确认后，移除了手动节点连通测试（卡片、行内按钮、后台 `probe`）；原 Issue 中“保留手动测试”一条据此调整，已在 Issue 中记录。汇总卡片的分级仍按中位延迟计算。
用户反馈：鼠标悬停在折线上看不到时间和数值。已改为让样本记录每轮的 `observedAt`，展开后的详细曲线支持悬停，显示竖线、圆点和“时间 · 延迟”标签，未回复的点显示“无回复”。新增时间解析测试，用户实机确认悬停正常。
